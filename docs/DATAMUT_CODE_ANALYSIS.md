# DATAMUt Code Analysis — findings and implications for the θ↦δ mapping

*Roger N. Anaedevha · 24 July 2026 · based on the source Federico sent (`datamut_analysis.h`, 588 lines; `datamut_paper_exact_demo.cc`, 999 lines). Compiled clean with g++ 13 / C++17 and verified running (grid scenario, 3 seeds: perfect detection, 0.1–0.24 ms per policy run).*

## 1. What the code actually is

Despite the archive name (`Datamute_NS3.zip`), this is **not an NS-3 module**. It is a self-contained C++17 discrete-event replay of the paper's detection logic, with no NS-3 dependencies whatsoever. That is good news for us: it compiles anywhere in one command, runs in milliseconds, and is trivially scriptable for θ-sweeps — no NS-3 build environment needed. It also means the "network simulation" is an abstract packet-hop model, not a radio/PHY simulation; anything RF-level (jamming intensity, link budget) lives on my side of the interface, which matches the division of labour. One question for the student who wrote it: whether an NS-3 integration exists elsewhere, or whether this replay *is* the paper's evaluation vehicle.

The architecture has four parts. **TimeWindowGraph** implements the paper's TWiG: periodic encounter windows (default 60 s cycle) between node pairs; `ComputeExpectedRoute` is a Dijkstra over earliest-arrival times through the windows — this is the deterministic "expected behaviour" oracle. **DelayModel** injects benign forwarding delay U[0.05, 0.18] s at every hop and malicious extra delay U[1.0, 7.0] s at attacker-controlled hops, with counter-based deterministic seeding (same seed ⇒ bit-identical run — excellent for reproducibility and for our multi-seed statistics). **Route policies** (AODV = always recompute; OLSR/DSDV = periodic cache refresh at 12 s / 18 s; DSR = cache forever) determine the *expected* next hop the detector compares against. **Two detectors**: `PaperExactDetector` (the one the demo runs) flags a hop as suspicious if `residual = observed_send − expected_send > ε` **or** the observed next hop differs from the policy's expected next hop, and flags a *node* after a single suspicious hop; `MaliciousDetector` (in the header, unused by the demo) is a softer variant with per-node adaptive thresholds (mean + kσ calibrated from benign residuals via `ThresholdCalibrator`) and a breach count ≥ 2 before flagging.

Three built-in topologies are selectable via `DATAMUT_SCENARIO`: 4×4 grid with sink n17 (attackers n6, n10), a 9-node ring (attackers n3, n4), and a double ring of 15 nodes (attackers n3, n5). Seeds and counts come from `DATAMUT_SEED`/`DATAMUT_SEED_BASE`/`DATAMUT_NUM_SEEDS`. Outputs are stdout hop logs plus per-seed and aggregate CSVs (tp/fp/fn/tn, precision, recall, F1, FPR, execution time by protocol).

## 2. The detector's operating point θ — precisely identified

The single scalar that plays the role of θ in our composition is **`deviationEpsilonSeconds`, hard-coded to 0.25 s** in `ExperimentRunner::Run()`. A time-delay attacker evades detection at a hop iff its total forwarding delay stays ≤ ε (path deviation is a separate, orthogonal trigger). Two structural facts matter for the theorem:

**First, the residual budget is per-hop and additive.** An evading attacker can inject up to ε − d_benign extra delay at *every* hop it controls without ever tripping the detector. With H malicious hops on the route, the worst-case undetected cumulative delay is bounded by **Δ(θ) ≤ H·θ** (conservatively; tighter with the benign floor subtracted). This is exactly the clean, provable quantity the composition needs: θ is a knob, Δ(θ) is linear in it, and H is bounded by route length, which TWiG lets us compute deterministically.

**Second, there is a discontinuity the theorem must respect.** Delay is not only additive latency: if the injected delay pushes the send past the encounter window's end, the packet waits a *full TWiG period* (60 s here) for the next cycle — the demo logs these as "missed opportunity" events. So the residual-attack effect is piecewise: Δ(θ) = H·θ while θ stays under the window-slack margin, then jumps by one period per missed window. The honest worst-case bound is Δ(θ) ≤ H·(θ + P·1[θ > slack_min]). This discontinuity is actually a *feature* for the paper: it gives the certified-MCR-vs-θ curve a knee, which makes the "neither layer alone" story visually sharp.

**Third, the demo's default configuration has zero detection-side slack to trade.** With malicious delay ≥ 1.0 s and ε = 0.25 s, every malicious hop is caught (we verified: 24/24 flagged, precision = recall = 1.0 across all four policies and all seeds). The paper's evaluation regime is separated — attack floor 4× above threshold. For our work the interesting regime is the *adversarial* one: an attacker who knows ε and injects just under it. That attacker is invisible to DATAMUt *by construction*, and quantifying what it can still do to the mission is precisely Option A's contribution. This framing — "we take Federico's detector at face value and characterise what survives it" — respects his design and needs no changes to his code.

## 4. How this feeds the interface mapping (Week 3 preview)

The chain the theorem will formalise: at operating point θ, the worst undetected network effect is a cumulative forwarding delay Δ(θ) (Section 2). A delayed C2/correction packet means the navigation stack operates on state that is **stale by Δ(θ)** seconds; at bounded UAV speed v_max, stale state of age τ implies a position/state perturbation **δ ≤ v_max · τ = v_max · Δ(θ)** — a bounded input perturbation in exactly the form the Lipschitz–Grönwall certificate consumes (bounded input ⇒ bounded trajectory tube ⇒ bounded MCR loss). Week 3 replaces the v_max·τ bound with an empirically grounded version from the UAV Attack Dataset (measured position degradation under real GPS spoofing/jamming/DoS on the same PX4 family), which will be tighter than the kinematic worst case. The proof-of-concept pairing record already in the repo (`data/staging/pairings.jsonl`) exercises this chain end-to-end with the placeholder mapping, so the schema, the plumbing, and the certificate hook-point are all in place before the theorem work starts.
